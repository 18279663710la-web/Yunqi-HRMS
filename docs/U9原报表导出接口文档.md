# U9 原报表导出接口文档

## 1. 文档状态与目标

本文是供 U9 服务器侧调研、开发和联调用的**建议接口规范**，不是现有接口说明；接口地址、U9 报表名称、实际导出能力和实现方式均须由 U9 侧确认。当前本项目通过 SQL 查询及 U9 汇总存储过程取得数据，再自行生成 PDF，**尚未接入 U9 原报表文件**。

业务员 U9 模块暂时收尾；本文保留为后续确认和对接的依据，不表示原报表导出已经实现。

目标是在员工小程序下载以下三类文件时，由 U9 侧生成或提供与 U9 界面原生导出一致的 PDF：

1. 应收单。
2. 收款单。
3. 应收款汇总表。

“原报表”指使用 U9 实际使用的报表或打印模板和原生导出机制生成的文件，保留其实际字段、版式和分页；不是调用方根据 SQL 结果重新排版制作的近似 PDF。能否做到以及每类报表对应的模板和导出方式均待确认。若 U9 原生不支持 PDF，先说明可用格式和转换方案，双方确认后再调整契约；不得把其他格式改扩展名冒充 PDF。

## 2. 对接关系与现有口径

```text
员工小程序 → 本项目服务端 → U9 侧报表导出接口 → U9 原报表或打印引擎
                                ↓
员工小程序 ← 本项目服务端 ← PDF 文件流
```

- 小程序继续只访问本项目服务端；本项目验证员工会话、当前职务及绑定关系，再由服务端访问 U9 侧接口。本文接口为**服务端之间的建议接口**，不是现有小程序 API，U9 地址和服务凭据不下发到小程序。
- 本项目员工 ID 与 U9 业务员 ID 的映射保存在本项目 MySQL。请求中的 `operatorId` 由本项目服务端查绑定得到，不能由小程序直接指定。它是 U9 `CBO_Operators.ID`，不是业务员编码 `Code`，统一按字符串传递，不能转为 JavaScript 数字。
- 应收单和收款单现有列表依据出货明细业务员归属；汇总表使用 U9 原报表过程并按客户当前负责人、业务员所属组织和会计期间筛选。这两种归属口径不同，U9 侧需核实原报表能否实现相同范围。
- 单据 `documentId` 是当前列表对应的 U9 单据头 ID，不是单据编号；如原生导出只接受编号或其他标识，U9 侧需说明可靠映射方式。
- 当前项目连接 U9 的用途为读取；新增接口不得以导出为由修改 U9 永久业务数据。U9 侧需检查实际报表过程、导出组件及其数据库权限是否满足此约束；只读连接意图本身不是权限保证。

## 3. 通用约定

以下路径和字段名为建议值，待双方确认。使用 HTTPS 或经双方认可的受保护内网连接，接口仅允许受信任的本项目服务端调用。

| 项目 | 约定 |
| --- | --- |
| 基础路径 | `/api/u9/report-exports/v1`，部署地址待定 |
| 请求方法 | `POST` |
| 请求类型 | `Content-Type: application/json; charset=utf-8` |
| 服务认证 | `Authorization: Bearer <服务间访问令牌>`，令牌由服务端配置，具体发放与轮换待双方确认 |
| 请求标识 | `X-Request-Id: <请求标识>`，建议使用唯一 ID；响应原样带回，便于排查 |
| 成功响应 | HTTP 200，响应体为完整 PDF 二进制，不包装为 JSON 或 Base64 |
| 响应头 | `Content-Type: application/pdf`、`Content-Disposition: attachment; filename="...pdf"`、`Cache-Control: no-store` |
| 同步时限 | 建议双方以 60 秒为初始联调目标；若 U9 导出需要更长时间，另行设计异步任务接口，不能假定已支持 |

所有示例 ID、期间、令牌和路径仅用于说明。接口必须使用受控的服务间身份；`operatorId` 是业务筛选和权限校验参数，**不是认证凭据**。服务凭据、员工令牌和报表内容不写入 URL 或普通日志。

## 4. 应收单原报表

**建议路径**：`POST /api/u9/report-exports/v1/receivables/pdf`

请求：

```json
{
  "operatorId": "101",
  "documentId": "201"
}
```

| 字段 | 类型 | 必填 | 含义与校验 |
| --- | --- | --- | --- |
| `operatorId` | string | 是 | U9 业务员内部 ID，1–19 位十进制数字，值必须是 U9 中有效 ID |
| `documentId` | string | 是 | U9 应收单头内部 ID，1–19 位十进制数字，值必须是 U9 中有效 ID |

U9 侧应核对单据存在且该业务员符合双方确认的访问范围，再返回此单据的 **U9 原生应收单 PDF**。原报表的名称、字段、状态过滤和是否能按业务员限制明细，需在联调前确认。

## 5. 收款单原报表

**建议路径**：`POST /api/u9/report-exports/v1/receipts/pdf`

```json
{
  "operatorId": "101",
  "documentId": "301"
}
```

参数类型和校验规则与应收单相同，其中 `documentId` 为 U9 **收款单头**内部 ID。U9 侧应核对单据存在及访问范围，再返回该单据的 **U9 原生收款单 PDF**。

目前本项目的收款归属通过核销明细关联应收及出货明细；U9 侧需要确认原报表中的收款单与此单据 ID 一致，并确认未核销、部分核销和一单多业务员等情况的可导出范围。

## 6. 应收款汇总表原报表

**建议路径**：`POST /api/u9/report-exports/v1/receivables-summary/pdf`

```json
{
  "operatorId": "101",
  "fromPeriod": "2026-01",
  "toPeriod": "2026-11"
}
```

| 字段 | 类型 | 必填 | 含义与校验 |
| --- | --- | --- | --- |
| `operatorId` | string | 是 | U9 业务员内部 ID，校验同应收单 |
| `fromPeriod` | string | 是 | 起始会计期间，格式 `YYYY-MM`，月份为 `01`–`12` |
| `toPeriod` | string | 是 | 结束会计期间，格式 `YYYY-MM`，月份为 `01`–`12`，不得早于起始期间 |

建议起止期间均包含在内；U9 侧需确认其报表期间定义与此一致，以及业务员所属组织的获取方式。由 U9 侧根据可信的业务员 ID 确定组织和客户范围，生成对应筛选条件的 **U9 原生应收款汇总表 PDF**，不得允许调用方传入任意 SQL 或筛选表达式。

现有实现调用 `dbo.SP_HIARC_Rpt_JXYouke_CustomerRecInfo` 取得汇总数据，但这不证明该过程本身能够生成文件；需确认对应的 U9 报表模板、调用参数和导出入口。

## 7. 权限与跨业务员单据

本项目服务端负责员工登录、实时职务和本系统绑定检查；U9 接口负责服务调用方认证，并根据可信的 `operatorId`、单据及汇总范围再次校验。不得只校验客户端提供的单据 ID 或业务员姓名。

**必须先解决原报表完整性与数据隔离之间的冲突：**如果一张 U9 原始单据包含多个业务员的明细，仅凭“当前业务员关联了其中一行”不能说明其有权查看整张单据。

双方应先确认 U9 原生报表是否支持只展示该业务员获准查看的明细，以及该筛选后的文件是否仍满足业务对“原报表”的要求。**在权限范围尚未确认、或原生导出无法限制到获准范围时，接口应拒绝导出并返回 `409 REPORT_SCOPE_UNCONFIRMED`，不得退回完整单据或自行生成替代 PDF。**如企业明确授权查看完整单据，须先确定并实现对应的授权规则，再开放。

对于不属于该业务员或不存在的单据，建议统一返回 `404 DOCUMENT_NOT_FOUND`，避免泄露其他单据信息。汇总表也必须确认客户及组织筛选没有扩大到其他业务员。

## 8. 错误响应

错误时返回 JSON，不能以 HTTP 200 返回错误页面或把 JSON 冒充 PDF。建议格式：

```json
{
  "code": "REPORT_SCOPE_UNCONFIRMED",
  "message": "该报表的数据范围尚未确认，暂不能导出",
  "requestId": "example-request-id"
}
```

| HTTP 状态 | `code` 示例 | 场景 |
| --- | --- | --- |
| 400 | `INVALID_ARGUMENT` | 参数缺失、格式错误、期间倒置或未知参数 |
| 401 | `UNAUTHENTICATED` | 服务间认证失败或凭据失效 |
| 403 | `FORBIDDEN` | 调用服务无权限，或业务员不满足导出条件 |
| 404 | `DOCUMENT_NOT_FOUND` | 单据不存在或不在业务员可访问范围 |
| 409 | `REPORT_SCOPE_UNCONFIRMED` | 多业务员等情况下无法确认原报表的数据访问范围 |
| 422 | `EXPORT_NOT_SUPPORTED` | 原报表或 PDF 导出能力不支持；不得返回替代文件 |
| 500 | `EXPORT_FAILED` | 报表生成失败 |
| 503 | `U9_UNAVAILABLE` | U9 数据库或报表服务不可用 |
| 504 | `EXPORT_TIMEOUT` | 报表生成超过服务端处理时限 |

汇总结果为空时，建议返回 U9 原生的空报表 PDF；如原生接口不支持，应约定明确错误，不生成本项目自制的替代报表。错误响应只返回可供定位的安全信息；详细错误由 U9 侧按请求标识记录，不向员工暴露数据库连接信息或报表数据。

## 9. U9 服务器侧需要确认的事项

1. 三类报表在 U9 中的实际名称、菜单位置、模板及导出步骤，是否有可供服务端调用的原生 API、SDK 或报表服务。
2. PDF 是 U9 原生导出、报表组件导出，还是打印/转换得到；能否在无交互、无桌面会话的服务器环境调用。若依赖额外组件、授权或权限，请列明。
3. 各接口需要的单据 ID、组织、账套、业务员、期间及其他必填参数，以及它们与本项目当前查询字段的对应关系。
4. 单据包含多个业务员时，原生模板能否按业务员限制明细；授权范围、完整单与筛选报表的业务要求如何确定。
5. 汇总表是否确实使用上述存储过程及其对应模板；客户当前负责人、组织和期间的口径与现有系统是否一致。
6. 生成过程是否只读取永久业务数据；报表服务身份、数据库权限、临时文件位置、清理机制、服务间认证和网络访问方式。
7. 最大文件大小、典型耗时、超时、并发能力、空结果和失败返回方式；如需要异步导出，另行约定任务接口。

## 10. 联调验收

使用获得授权的测试员工和测试数据，至少验证：

1. 三类文件均可打开，文件确实由 U9 原生机制生成；与 U9 界面使用同一参数导出的样本比较字段、版式、分页、金额及数据范围。因时间戳、元数据等变化，原则上比较业务内容和显示效果，不要求文件字节完全相同。
2. 应收单、收款单的 ID 映射正确；客户、币种、金额和对应业务员范围与双方确认的规则一致。
3. 汇总表覆盖起止月份，客户负责人、组织及金额与 U9 相同筛选条件下的结果一致；同时验证空结果和跨年期间。
4. 不同业务员相互访问、未绑定、非业务员、无效服务凭据及被禁用的访问均被拒绝；多业务员单据在规则未确认时不能下载。
5. 单据不存在、参数无效、U9 不可用、导出失败和超时能返回约定错误；响应和日志不泄露令牌或其他员工报表。
6. 验证报表生成过程不修改 U9 永久业务数据；临时文件按约定清理，且小程序最终能正常打开文件。

本文不要求直接修改 U9 数据库或新增某种特定服务器架构；U9 侧确认实际能力后，再根据结果调整接口及本项目对接实现。
